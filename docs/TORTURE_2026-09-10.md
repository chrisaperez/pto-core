# Torture audit — `fastq_stream` (`fastq_qc` / `fastq_trim`), 2026-09-10

Adversarial pass over the binary behind the cloud's `fastq_qc` (`--qc-only`) and
`fastq_trim` job types: input framing, the CLI, the SPSC pipeline, the SIMD
kernels, and throughput. Built as shipped (`FQ_ENABLE_HTS=ON`, `FQ_NATIVE=OFF`,
the wheel's and `pto-cloud/worker/Dockerfile`'s configuration), on Apple M4 Pro.

Every finding was reproduced against the pre-fix binary before it was patched.
`modules/fastq_stream/tests/test_cli.sh` passes **6 of 23** checks on the
pre-fix binary and 23/23 after; the `test_trimmer` additions cannot compile
against the old `accumulate_read` signature, so their pre-fix evidence is the
CLI repros below rather than a red run.

### F1 — output that is the input destroys it (Critical)

```
$ cp big.fq same.fq                      # 42,488,890 bytes
$ fastq_stream -i same.fq -o same.fq
fastq_stream: input ends mid-record: 172 trailing bytes do not form a complete FASTQ record
$ wc -c same.fq
0 same.fq
```

`open_output` used `O_TRUNC` after the reader had staged only 1 MiB. Same result
through a hard link. **Fix:** `refuse_output_aliasing_input()` compares
`(st_dev, st_ino)` of input and output — via `fstat` for `-` — before anything is
opened for writing. Skipped under `--qc-only`, which writes nothing.

### F2 — BGZF truncated between members (High)

A 2,000-read BGZF whose blocks end on record boundaries, cut after half its
blocks: `reads_in=1000`, exit 0. Member framing and CRCs are all intact, and the
assembler has no partial record to trip on. **Fix:** the reader requires the
28-byte EOF marker (`finish_bgzf`), as `samtools quickcheck` and `modules/peaks`
do. The flag is assigned per member, so an empty member mid-stream (concatenated
BGZF) is still legal — pinned by `test_truncated_compressed_input`. The test
suite's own `write_bgzf` omitted the marker and now writes it by default.

### F3 — truncated plain gzip (High)

`head -c -8` (no CRC32/ISIZE trailer) decoded with the CRC never checked, exit 0;
a file cut to 10 bytes, or to the 2 magic bytes, reported **zero reads**, exit 0.
`next_plain` treated end-of-input as end-of-stream. **Fix:** `member_open` tracks
whether input was fed since the last `Z_STREAM_END`; EOF inside a member throws.

### F4 — FIFO input corrupted by the format probe (High)

```
$ fastq_stream -i <(cat ok.fq) --qc-only
fastq_stream: malformed FASTQ record (expected '@id/seq/+/qual' ...)
$ cat ok.fq | fastq_stream -i - --qc-only       # same bytes via stdin: fine
```

`looks_like_alignment()` ran `hts_open` on the path, which reads a full hfile
buffer from a pipe and discards it on close. Affects every HTS-enabled build —
i.e. the wheel and the worker image. **Fix:** probe only `S_ISREG` paths; the
probe's htslib logging is also silenced (it printed `[E::hts_hopen] Failed to
open file` for ordinary FASTQs). A BAM over a pipe is no longer recognised;
`--help` now says so.

### F5 — thread creation failure aborts the process (High)

Reproduced with a `DYLD_INSERT_LIBRARIES` shim failing `pthread_create` with
`EAGAIN` after N successes (standing in for a container pids limit, or Linux
`RLIMIT_NPROC`, which counts threads): `libc++abi: terminating`, exit 134. The
`std::system_error` from `std::thread`'s constructor unwound past joinable
threads. **Fix:** all stages start through one vector inside a `try`; a failure
trips the error gate, the running stages leave their ring loops, every started
thread is joined, and the run exits 1 with `cannot start pipeline thread 4 of 8
... (lower --threads)`. Verified at budgets 0, 1, 2, 4, 5, 9, 11 under Release
and TSan.

### F6 — busy-waiting stages (Medium)

`Backoff` spun 128 times and then called `yield()` in a loop; `sched_yield`
returns immediately when nothing else is runnable. On plain gzip, where the
serial inflate is the only real work, 12 threads burned **19.8 CPU-seconds
(13.5 s of it system time) in 1.74 s wall**. **Fix:** spin, 16 yields, then
100 µs sleeps.

This is a trade, and the numbers are stated as such (median of 5 interleaved
runs; CPU is user+sys mean):

| Workload | Wall before → after | CPU-s before → after |
|---|---|---|
| plain gzip 450 MB, `-t 12` | 1.74 → 1.79 (+3%) | 19.7 → 3.6 (−82%) |
| BGZF 425 MB, `-t 12` | 0.33 → 0.31 | 3.56 → 1.58 (−56%) |
| BGZF 425 MB, `-t 4` | 0.89 → 0.92 (+3%) | 4.39 → 1.61 (−63%) |
| raw 425 MB, `-t 12` | 0.11 → 0.10 | 1.12 → 0.82 (−27%) |
| raw 425 MB, `-t 4` (1 worker) | 0.47 → 0.49 (+4%, see F7) | 1.84 → 0.66 (−64%) |

Shorter sleeps were measured and are worse on both axes — at 20 µs plain gzip
took 1.84 s / 6.0 CPU-s, at 1 µs 1.92 s / 14.0 CPU-s — because more wakeups
contend with the inflater. Output is byte-identical to the pre-fix binary.

### F7 — non-printable SEQ/QUAL bytes (Medium)

A quality line with NUL or `0xFF` bytes, or a NUL in SEQ, ran to exit 0: quality
bytes clamped to Q0 (and trimmed as merely low quality), SEQ NULs counted as `N`
and forwarded to the aligner. **Fix:** `simd::all_printable` (scalar/NEON/AVX2)
over SEQ and QUAL in `accumulate_read`, which now returns `ReadScan`; the worker
fails the run naming the read. `--missing-qual` is restricted to `'!'..'~'` so
the BAM path cannot synthesise a byte this rejects.

The check costs ~2% on the single-worker raw run. An earlier version that folded
it and Q20/Q30 into the scalar per-base loop cost **21%** (0.57 s vs 0.49 s at
the same backoff); the vector passes were kept, and the header comment records why.

### F8 — adapter options silently substituted (Medium)

The CLI's own comment calls silently substituting a value "its own defect"; four
adapter options did it:

- `-a ''` was dropped by `AdapterTrimmer::add` but still suppressed the defaults:
  adapter trimming off, report silent.
- `--adapter-seed 12` was clamped to `--adapter-overlap` (4).
- `--adapter-overlap 14` exceeds the 13 bp TruSeq default, which can then never match.
- `--adapter-mismatch 0.9` was accepted and clamped to 0.5 (8 mismatches in 13: not trimmed).

**Fix:** `validate_adapters()` rejects each (exit 2); `-a` also requires `ACGTN`.

### F9 — report write failures ignored (Medium)

`std::ofstream` sets `badbit` on EPIPE/ENOSPC and nothing checked it. **Fix:**
checked after `close()`; exit 1 (environment, not input). The output FASTQ's
`close()` is now checked too, since NFS reports deferred write errors there.
`test_cli.sh` stages this deterministically with `ulimit -f 1` and SIGXFSZ
ignored; a pipe whose reader exits early was tried first and is racy, since the
report fits in the pipe buffer.

**Contract note:** "cannot write report" previously exited **2**, which
`pto-cloud` maps to `invalid_input`. It now exits 1.

### F10–F13 (Low)

- **F10** `json_escape` handled only `\n` and `\t`; `-i $'a\rb.fq'` produced JSON
  `json.load` rejects. All bytes < 0x20 now escape as `\u00XX`.
- **F11** A final record missing its newline, or trailing blank lines, failed as
  "input ends mid-record". Carry with exactly three newlines and a non-empty
  last line gets its newline; an all-blank carry is ignored; anything else still fails.
- **F12** With `--window` > 0, `quality_trimmed` counted only window trims.
- **F13** `if (have < 18) break` dropped a short tail silently; `BSIZE+1` smaller
  than header+trailer was accepted as a member length.

### F14 — portable x86 builds are scalar (Info, fixed in pass 2)

`simd.hpp` dispatches at compile time on `__AVX2__`/`__AVX512BW__`. The wheel and
worker image build with `FQ_NATIVE=OFF` and no `-mavx2`, so on x86-64 every
kernel is the scalar loop — confirmed by building the header for x86-64 without
flags (`backend=scalar`). Fixing it means runtime dispatch the way
`scrna_matrix/simd_math.hpp` does (per-function `target` attributes). Not done
here: it cannot be benchmarked on this host.

## What did not break

- **SPSC ring / lane protocol.** Close-after-push ordering is correct (producer
  stores `tail_` before `closed`; consumer re-pops after seeing `closed`). No
  deadlock found on any abort path: every push and pop observes the gate. TSan:
  0 reports over 49 runs (9 inputs × 1–64 threads, plus forced spawn failures).
- **AVX2 kernels, executed for the first time.** The 2026-08-17 residual said the
  x86 SIMD paths had never run. Built with `-arch x86_64 -mavx2` under Rosetta:
  `sum_u8`, `count_ge`, `add_widen_u8_to_u32` and `mismatches` agree with a
  scalar reference over 48,160 cases (lengths 0–300), and `all_printable` over
  2,206,040. AVX-512 could not run (Rosetta has no AVX-512; SIGILL, as expected).
  All loads are `loadu`/`vld1q`, so alignment is not a concern.
- **Multi-GB streams.** 4.25 GB through a pipe: exactly 20,000,000 reads and
  2,000,000,000 bases counted, 10.9 MB peak RSS.
- **Mid-stream producer death** (`head -c N | fastq_stream`) fails closed.
- **Numeric bounds.** Negative, overflowing (`99999999999999999999`), NaN and
  trailing-junk arguments are all rejected with exit 2.
- **SIGPIPE on `--stdout | head -1`** exits promptly with `write failed: Broken pipe`.
- **ASan/UBSan** over every fixture at 1/3/16 threads (51 runs) and a 400-input
  mutation fuzz: 0 reports. The fuzz is weak evidence — its mutations produced
  400 rejected inputs and no accepted ones, so it exercised the failure paths only.

## Residuals

- ~~F14~~ closed in pass 2, below; its AVX-512 half is compiled but unexecuted.
- **BAM through a pipe** is not detected (F4's trade); it fails as malformed FASTQ.
- **Malformed input exits 1**, where `genomic_toolkit` uses 2 for "the input was
  the problem". Changing it touches `pto-cloud`'s job contract and was not done.
- **BAM QUAL > 93** now reaches the printable check with its generic message
  rather than a BAM-specific one; not separately tested.
- **Adapter matching is case-sensitive against the read**: a lowercase
  (soft-masked) adapter copy is not trimmed. Unchanged.

# Pass 2 — runtime dispatch, the output guard, and `pto-peaks`

Same day, three objectives: close F14, turn F1's guard into something every

finding below was reproduced against the pre-change binary or header first;

## F14 closed — runtime SIMD dispatch in `fastq_stream`

`simd.hpp` now carries scalar, NEON, AVX2 and (opt-in) AVX-512BW kernels in
namespaces, each x86 kernel under a per-function `target` attribute, and picks
one set once from CPUID -- the arrangement `scrna_matrix` and `peaks` already
use. `FQ_FORCE_ISA=scalar|neon|avx2|avx512` pins it; `*_isa()` entry points let
the tests drive every ISA the CPU can execute; `simd_backend` in the JSON
report now names the ISA that actually ran.

## The output guard, in every binary that writes a file

The request was one header under a shared `modules/common/`. `pto-core/CLAUDE.md`
forbids exactly that (modules share no code; a shared layer was tried and
reverted), so there is **one `file_identity.hpp` per module**, identical but
for the namespace, each with its own tests: `fastq_stream`, `peaks`,
`genomic_toolkit`, `cuttag_profiler`. Named paths are compared with
`std::filesystem::equivalent` after existence and regular-file checks; `"-"` is
compared through `fstat` of the descriptor.

**That last half was found by a test, not designed.** The first version
resolved `"-"` as `/dev/stdin`/`/dev/stdout`. On macOS that path does not
resolve to the redirected file, so `pto-peaks -o x.bed < x.bed` passed the check
and overwrote `x.bed` -- and moving `fastq_stream` onto the helper had silently
regressed its own F1 fix, which had used `fstat`. The peaks CLI test caught it;
`test_dash_is_asked_of_the_descriptor` now `dup2`s a file onto stdin in every
module's suite.

| `pto-peaks` | `-o` = input BED, = `--chrom-sizes`, = the file stdin reads: **exit 0, input replaced by the narrowPeak** | refused, exit 1 |

### P2 — end of input that was not

`run_bed` looped on `std::getline`. A 300 MB input with no newline was read
into one string (704 MB resident) before being refused. Under an allocator that
refuses requests over 64 MB -- a stand-in for a container memory limit, since
macOS enforces none -- `getline` turned the failed allocation into a failed
stream, the loop took that for EOF, and the run **exited 0 reporting 0
fragments and 0 peaks**. Fix: a line reader that cuts lines out of a 4 MiB block
with `memchr` straight from the stream buffer, refuses a line over 1 MiB
(exit 2), and allocates nothing per line; `main` now catches what escapes.
An `istream::getline` version was measured first and was 4% slower than the
original (5.25 s vs 5.05 s on 6M fragments); the block reader is 2% faster
(4.97 s vs 5.07 s), narrowPeak byte-identical.

### P3 — the iteration cap

`kMaxIterations` was 100,000 with a comment saying that "covers every k a pileup
can hold". `PeakCaller::clamp_count` passes k up to 2^32 - 1, and near
lambda = k the series needs ~sqrt(2k ln 1e18) terms, about 600,000 there.
Against mpmath at 40 digits:

| k | lambda | exact -log10 p | before (all kernels) | after |
|---|---|---|---|---|
| 1e8 | 99,960,000 | 4.50025 | 4.50025 (rel. err 3e-8) | unchanged |
| 1e9 | 999,873,508.8 | 4.49963 | **0** | converged |
| 2^32-1 | 4,294,705,151 | 4.49947 | **0** | converged |
| 2^32-1 | 4,294,574,079 | 9.00634 | **0** | converged |
| 2^32-1 | 4,294,377,471 | 18.9491 | **0** | converged |

Now `1 << 20`. `test_sf_converges_at_the_count_ceiling` pins those values
(tolerance from the suite's own `poisson_tolerance()`); against the HEAD header
it fails 16 checks, and passes on arm64 (NEON, scalar) and on x86-64 under
Rosetta (AVX2, scalar). Cost, measured: the worst case, k = lambda = 2^32 - 1,
is 0.96 ms scalar / 0.33 ms per NEON lane; k = 1e6 about 10 us; a typical peak
base unchanged; the Poisson suite 0.28 -> 0.35 s. Severity is Medium, not High,
because no sequencing run produces a pileup of 1e9 -- but the caller explicitly
accepts one, and the failure was silent.

### P6 — BAM header contigs

`read_header` accepted `l_name == 1` (an empty name, written as an empty column
1), duplicate names (two contigs' peaks under one name) and `l_ref == 0`. The
chrom.sizes loader refuses all three and the SAM spec forbids all three; the
two front ends now agree. Three new cases in `test_bam_streamer`, 5 failures
against the old header.

## What did not break (`pto-peaks`)

- **Ring buffers across contig boundaries.** One `MultiScaleWindow` reused
  across 69 contigs (23 lengths x 3 rounds: 1 bp; either side of 1 kb, the
  4,096 bp fragment cap, the 5 kb half-window, 10 kb, the 16,384 slot ring and
  twice it; up to 131 kb), with fragments hugging both contig ends, piles of 50
  identical fragments, and gaps longer than the ring, checked at **every base**
  against a prefix-sum reference: 466,224 checks, 0 mismatches, before any
  change. Kept as `test_one_window_reused_across_contigs_matches_the_reference`.
- **Poisson extremes.** A 255-point grid, k in {1 .. 2^32-1} (including the
  64/65 and 512/513 table seams) x lambda in {5e-324 .. DBL_MAX}: no non-finite,
  negative or float-overflowing score, and no ASan/UBSan report. There is no
  integer path to overflow: the log-factorial index is bounded before the
  gather (existing test), the reciprocal table only serves k <= 64, and the
  largest reachable score (~1.4e12) is far inside float range.
- **Scalar vs vector at the ceiling.** After P3's fix the same grid shows two
  scalar/NEON disagreements, both at k ~ lambda ~ 2^32: 0.3010345 (scalar) and
  0.3010279 (NEON) against an exact 0.3010282. That is 6.6e-6 in -log10 p,
  inside the header's own error model (eps times the largest term, a tolerance
  of 1.2e-3 there), at p ~ 1/2 where no call is made. Pre-existing rounding,
  not a defect.
- **The AVX2 Poisson and caller kernels, executed for the first time**, under
  Rosetta: 154,799 and 326,373 checks, 0 failures.
- **Out-of-order input** is refused as documented: a record behind its
  predecessor, and a contig that reappears, both exit 2 (existing CLI cases).
- **Zero-length contigs in BED input** were already refused by the sizes loader.

## P8, completed — the no-BGZF build (2026-09-11)

P8's diagnostic lived inside the BGZF branch, after `bam.open()` fails. A build
with `PEAKS_WITH_BGZF=OFF` returns before that, at the `!BamStreamer::available()`
check, with exit **1** and "rebuild with libdeflate or zlib" -- so the fix
never reached the build a bare cluster produces, which is where
`fragments.tsv.gz` most often arrives. Every local run used a BGZF build, so
`test_cli.sh`'s "a gzipped fragment BED exits 2" passed everywhere except
`ci.yml`'s "peaks builds without BGZF" step, which has been red since this
audit landed.

**Fix.** That branch now prints the same `zcat` hint (plus the rebuild line, for
a real BAM) and exits **2**, so one input gets one exit code whatever the build
flags -- the property `job_specs.RETRYABLE_EXIT_CODES` and Nextflow's
never-retry-2 rule assume. No test changed: the test was right.

| chr22 slice vs `pto-peaks`' own chr22 calls | 22,473 / 66,467 | 0, exit 2 "chromosome-naming mismatch" | 22,473 |

The second row's diagnostic is wrong as well as the count: the names match;
the numbering does not.

**Cause.** `main.cpp` pre-seeds the stream's `ContigDict` with the peak file's
contigs, so fragments from text input resolve against peaks. `stream_bam` then
interned the header and wrote `f.tid = rec->core.tid` under the comment "a
Fragment's tid IS the BAM's tid" -- true only for an empty dictionary. chr22
(BAM tid 21) was queried as whatever the peak file's 22nd contig was.

**Why nothing caught it.** Every in-tree BAM (`demo.bam`, `bench.bam`, the
region-partition fixture) has one contig, where both numberings are 0.
`make bench-gold`'s tiers that ran use those. The multi-contig
`gtk/frip-vs-bedtools` validation case on `ENCSR000AKA` would have failed;
no recorded run of it exists in `reports/`.

**Fix.** `stream_bam` builds a header-tid -> dictionary-id table once and
writes the dictionary id. A record whose tid is negative or past the header is
counted malformed rather than indexed. `sizes`/`markdup` are unaffected in
result (they need ids only to be consistent) and pass unchanged.

**Regression.** `scripts/validate_bam_contig_order.sh` (ctest
`gtk_bam_contig_order`, htslib-gated like `gtk_region_partition`): two contigs,
fragments at different positions on each, a peak file listed in reverse. The
first version put both contigs' fragments at identical positions, so the
swapped lookup scored the same count and the script passed against the pre-fix
binary; it was corrected and now fails on it (20/0 vs 20/4).

**Exposure.** Every `genomic_toolkit` built before this change, including
build trees and wheels made earlier today, and any `pto-cloud` worker image or
Nextflow container built from them. A FRiP from any of them on a real
multi-contig BAM should be recomputed.
