# Adversarial audit — 2026-08-17

Fuzzing, sanitizer, concurrency and numeric-boundary sweep across all four
modules. Five defects found and fixed, one false positive run to ground and
documented, and four permanent regression suites added.

This document follows the convention of [`REVIEW_2026-08-15.md`](REVIEW_2026-08-15.md)
and [`SECURITY_HTTP_2026-08-15.md`](SECURITY_HTTP_2026-08-15.md): it is a
living record. Extend it rather than replacing it.

**Scope.** Every finding below was reproduced before it was fixed, and the
reproduction is recorded so it can be re-run. Nothing is listed on suspicion.
Where I could not reach a defect through the public API I say so explicitly
rather than implying an exploit I do not have.

### What did *not* break

Recorded because a clean result from a serious attempt is evidence, and
because the next auditor should not repeat this work:

- **`PeakSet` overlap arithmetic.** 20,000 random peak sets × exhaustive
  queries over every `[qs, qe)` pair, differentially checked against a
  per-base bitmap under ASan+UBSan: zero mismatches in `overlaps()` and
  `overlap_bases()`, including nested, book-ended and zero-length intervals.
- **`Block_CSR` input validation.** `from_raw()` already rejects NaN/Inf and
  caps `||row||²` at 1e34; this is what makes T5 unreachable in practice.
- **SIMD kernel exactness.** `dense_dot` and `gather_dot` swept over every
  length 0–200 (crossing all NEON/AVX tail boundaries) against a double
  reference: no divergence beyond float accumulation error.
- **Cosine symmetry and self-similarity.** 7,000 random sparse pairs:
  `cos(a,b) == cos(b,a)` and `cos(a,a) == 1` held throughout.
- **`fastq_stream` concurrency.** 96-thread runs over 8 adversarial inputs
  (single record, 20k tiny records, sub-Phred quality bytes, high-bit quality
  bytes, empty sequences, empty file) under TSan: zero races.
- **`cuttag_profiler` determinism.** Bit-identical output across 1, 2, 3, 7,
  16, 64 and 96 threads.
- **Record-length fail-closed.** A read exceeding the 64 KiB carry limit is
  refused with a message naming the limit — the pattern T4 adopts.
- **File-descriptor exhaustion.** At `RLIMIT_NOFILE=4` both tools fail closed
  with a clear message and no leak; they succeed again at 6.

## T1 — Undefined behaviour in `trim_sliding_window` (High)

**Where.** `modules/fastq_stream/include/fastq_stream/phred_calculator.hpp`

The window threshold was computed as:

```cpp
const uint32_t limit = static_cast<uint32_t>(min_mean * static_cast<double>(window));
```

`static_cast<uint32_t>(d)` is undefined behaviour whenever the truncated value
of `d` is not representable — which covers **every negative value, every value
past 2³², and NaN**. `--window-mean` was parsed with `strtod` and passed
through unvalidated, so all three are reachable from the command line.

**Reproduction** (ASan+UBSan build, `-fno-sanitize-recover=all`):

```
$ fastq_stream -i one.fq --qc-only --window-mean -5
phred_calculator.hpp:190:29: runtime error: -20 is outside the range of
    representable values of type 'unsigned int'

$ fastq_stream -i one.fq --qc-only --window-mean 1e30    # 4e+30
$ fastq_stream -i one.fq --qc-only --window-mean nan     # nan
```

Three distinct UBSan reports. This is the only UB found: a sweep of all fifteen
numeric options produced no other report.

**Fix.** The threshold is now range-checked *before* the narrowing cast. NaN is
tested first and explicitly, because every comparison against NaN is false and a
plain `min_mean <= 0` test would fall straight through to the cast.

A second, subtler bug was introduced and caught while writing the fix: clamping
`limit` to `UINT32_MAX` made the later `offset + limit` overflow in `uint32_t`
and wrap to `offset - 1`, **inverting** the comparison on exactly the extreme
input the clamp existed to handle. The rolling sum and threshold are now
compared in `uint64_t`, where neither term can overflow.

**Also fixed at the boundary.** `main.cpp` now rejects the argument outright
(T3). Both layers are kept: this is a public header that the tests and any
library consumer call directly, and a validated CLI is not a property the
kernel can assume.

## T2 — MAPQ filter fails open on a corrupt BEDPE column (Medium)

**Where.** `modules/genomic_toolkit/src/fragment_stream.cpp`, `stream_bedpe`

```cpp
std::int64_t mapq = 255;
if (n >= 8) parse_int(fields[7], mapq);   // return value discarded
if (mapq < filter.min_mapq) { ++stats.dropped_mapq; continue; }
```

The result of `parse_int` was discarded, which failed open two different ways:

| Column 8 | Actual behaviour | Should be |
|---|---|---|
| `XX` | parse fails, `mapq` keeps its `255` initialiser → passes `--min-mapq 30` **as a perfect alignment** | rejected |
| `60abc` | `std::from_chars` writes the parsed prefix *before* reporting trailing junk, so the discarded `false` left `mapq = 60` | rejected |

A corrupt or mis-delimited BEDPE therefore sailed through the exact filter the
user set to protect against it. `parse_int`'s own docstring says accepting a
partial parse "is how a mis-delimited file becomes a plausible wrong answer
instead of an error" — the call site simply did not honour it.

**Reproduction.** Five-line BEDPE (`Q60`, `XX`, `60abc`, `.`, absent) at
`--min-mapq 30`: before, all five emitted fragments; after, three emit and two
are counted malformed.

**Fix.** The parse result is honoured. An *absent* column, and the BEDPE `.`
placeholder, still mean "not recorded" and pass at 255 — there is nothing to
filter on. A *present* but unparseable column (including empty) is a corrupt
record and increments `malformed_lines`, so the report shows the user their
file is broken rather than their data being bad.

**This is the recurrence pattern `REVIEW_2026-08-15.md` warns about.** The
sibling `copies` column in `stream_fragment_bed`, ~50 lines below, already
checked its parse *and* clamped the result. The same check was simply missing
from the neighbouring function. I grepped every other `parse_int` call site in
the module; these were the only two, and the other is correct.

## T3 — Numeric CLI options silently truncate (Medium)

**Where.** `modules/fastq_stream/src/main.cpp`

Every numeric option was parsed and then narrowed with an unchecked cast:

```cpp
cfg.tail_q = static_cast<uint8_t>(parse_long(value(argc, argv, i), "--trim-tail"));
```

`--trim-tail 300` truncates through `uint8_t` to 44 and runs silently at a
threshold the user never asked for. Demonstrated on a 40-base quality ramp:
`--trim-tail 300`, `--trim-tail 556` and `--trim-tail 44` all produce
`bases_out=0`, i.e. 300 and 556 are indistinguishable from 44.

**Fix.** `parse_long_in` / `parse_double_in` range-check and reject. The double
variant is written as a *positive* test (`!(v >= lo && v <= hi)`) so NaN — for
which every comparison is false — is rejected rather than slipping through a
negated check. Ranges are per-option and physically motivated (Phred 0–93,
rates 0–1, threads 0–4096).

```
$ fastq_stream --trim-tail 300 ...
fastq_stream: value out of range for --trim-tail: 300 (expected 0..93)
```

## T4 — Unbounded line-buffer growth (Medium)

**Where.** `modules/genomic_toolkit/src/line_reader.hpp`

`refill()` doubled the buffer whenever a single line did not fit, with no
ceiling. The doubling itself is right — a fixed buffer would silently split a
long line into two malformed records — but the growth was driven directly by
untrusted input.

**Measured before the fix**, on files consisting of one unterminated line:

| Line length | Peak RSS |
|---|---|
| 25 MB | 70 MB |
| 50 MB | 134 MB |
| 100 MB | 262 MB |
| 200 MB | 518 MB |

Roughly 2.6× the line length (doubled buffer plus the `memmove` tail), scaling
until the process is killed. A binary file read as text, a truncated download,
or a hostile BED all reach it.

*Honesty note:* I could not demonstrate the `std::bad_alloc` path itself —
macOS does not enforce `RLIMIT_AS`, so the allocation succeeded at every limit
I set. The RSS amplification above is measured; the OOM outcome is inferred
from it.

**Fix.** Growth stops at 64 MiB and throws with the byte count. `fastq_stream`
already solved this in the same shape — it refuses a record past its 64 KiB
carry limit rather than growing to meet it — so this is that established rule
applied to the module that was missing it. 64 MiB is four orders of magnitude
above any real fragment record.

## T5 — `cosine_from_dot` can return `+inf` (Low, defence-in-depth)

**Where.** `modules/scrna_matrix/include/matrix/simd_math.hpp`

```cpp
const WideAcc<T> r = static_cast<WideAcc<T>>(dot) / denom;
if (!std::isfinite(r)) return T{0};
return static_cast<T>(r);          // <-- can overflow to inf
```

`WideAcc<float>` is `double`, so the guard checked finiteness of the **wide**
quotient and then returned it **narrowed**. A quotient that is finite in double
can overflow float on the cast:

```
cosine_from_dot(1.0f, FLT_DENORM_MIN, 1.0f)
    r = 1.0 / 1.4e-45 = 7.1e44     finite as a double, passes the guard
    (float)r          = +inf       returned to the caller
```

Also reproduced with `(1, 1e-30, 1e-20)`, `(1e30, 1e-20, 1e-20)` and
`(FLT_MAX, 1e-20, 1)`.

This defeats the guard's own documented contract — "a similarity that cannot be
represented is reported as no similarity, never as NaN". An infinite score is
in one respect *worse* than a NaN: it is a valid, totally-ordered value, so it
does not trip the `sort_heap` precondition the comment cites. It silently wins
the top-k and makes a degenerate row the nearest neighbour of everything.

**Reachability — stated plainly.** I could **not** reach this through the
public API. `Block_CSR::from_raw()` rejects non-finite values and caps
`||row||²` at 1e34, and for a consistent (dot, norm, norm) triple
Cauchy–Schwarz bounds the ratio at 1. Attempting it with subnormal row values
short-circuits earlier: the float dot product underflows to 0 and the
`dot == 0` early return fires. This is a latent defect in a guard, fixed as
defence-in-depth for direct callers of a public header, not an exploitable bug.

**Fix.** Re-check finiteness *after* the narrowing cast. One predictable
compare on a path that already branches twice.

## T6 — TSan races in the FRiP reduction (false positive)

`genomic_toolkit frip` under TSan reports 20–40 data races in
`FripCounter::add_batch` at `frip.hpp:105–106`, inside `.omp_outlined` and
`.omp.reduction.reduction_func`, reached from `__kmp_hyper_barrier_gather`.

**It is a false positive from an uninstrumented libomp**, on four independent
pieces of evidence:

1. The reported location is *"stack of thread T\<n\>"* — libomp's private
   per-thread reduction copies, not shared state. The loop's only shared write
   is `f.flags |= kInPeak` on `data[i]` under a static schedule, so no two
   threads touch the same `Fragment`.
2. The non-libomp frames are compiler-generated OpenMP thunks.
3. `OMP_NUM_THREADS=1` under TSan reports **zero** races — with no combine step
   there is nothing to misread.
4. Rebuilding with `-DCMAKE_DISABLE_FIND_PACKAGE_OpenMP=ON` under TSan reports
   **zero** races and produces byte-identical output.

Correctness was established independently of the sanitizer: **55 runs** of a
200k-fragment workload across **11 thread counts (1–128)** produced exactly
**one** distinct JSON result. A broken `reduction(+:...)` drifts; this does not.

**No suppression was added, deliberately.** `docker/tsan.supp`'s own scope rule
forbids suppressing any report touching `modules/*/src` or `modules/*/include`,
and these frames are first-party. A `race:frip.hpp` rule would also blind the
harness to a genuine race later introduced into that file — precisely the
failure the negative control in that file's section 1 was written to catch. The
investigation and its evidence are recorded in `docker/tsan.supp` §4 instead, so
the next person re-verifies in a minute rather than re-investigating for a day.

## Regression tests added

| Test | Covers |
|---|---|
| `modules/genomic_toolkit/tests/test_fuzz_parsers.cpp` (new suite `gtk_fuzz_parsers`) | T2, T4; seeded mutation fuzzer over BEDPE and fragment-BED with coordinate/arity/encoding mutations, plus emitted-fragment invariants |
| `modules/fastq_stream/tests/test_trimmer.cpp` → `test_sliding_window_threshold_domain` | T1; negative/zero/NaN/infinite/1e300 thresholds, and the `uint64_t` saturation that the first fix got wrong |
| `modules/scrna_matrix/tests/test_matrix_ops.cpp` → `test_cosine_from_dot_never_returns_non_finite` | T5; eleven degenerate (dot, norm, norm) triples, all required finite and in [-1, 1] |
| `docker/tsan.supp` §4 | T6; the evidence and the re-verification recipe |

The fuzzer is a deterministic seeded mutation harness, not a libFuzzer target:
libFuzzer's runtime is not shipped with Apple clang, and a harness that only
runs where a coverage-guided engine is installed does not run in CI on this
project's own machines. A fixed seed also makes failures reproduce exactly.

It asserts, after every input, the invariants the rest of the module assumes
without checking: `0 <= start <= end <= kMaxCoord`, `length() > 0`, the filter
is satisfied, every `tid` indexes the dictionary, and `fragments_emitted`
matches what the callback actually received.

**A bug in the shared test harness was fixed in passing.** `testing::g_checks`
and `g_failures` were `int`; the fuzz suite is the first to drive enough checks
to overflow them (observed: `-1676887498 checks`, signed overflow — itself UB).
Both are now `long long`, and the fuzz path folds per-fragment invariants into
one check per input so the summary stays readable.

## Residuals

Honest list of what this pass did **not** establish:

- **`std::bad_alloc` resilience is untested.** macOS does not enforce
  `RLIMIT_AS`, so no allocation failure could be induced. T4 removes the
  largest input-driven allocation, but the general behaviour under allocator
  failure remains unverified. Doing this properly needs a Linux runner with
  `RLIMIT_AS`, or an allocator shim.
- **AVX2 / AVX-512 paths were exercised only via `SCRNA_FORCE_ISA` on arm64**,
  which selects the scalar fallback rather than the x86 kernels. The x86 SIMD
  code was not executed by this audit; it needs an x86-64 runner.
- **The BAM/CRAM paths were fuzzed only through valid htslib-written files.**
  A malformed-BAM corpus targeting `bam_reader.cpp` and `stream_bam` is the
  obvious next pass — htslib does its own validation, but the fragment
  reconstruction on top of it (TLEN handling, mate coordinates) has not been
  driven with hostile records.
- **`cuttag_profiler`'s BED/GTF reader was not fuzzed.** It is the one parser
  in the repo this pass did not reach; it should get the same treatment as
  `test_fuzz_parsers.cpp`.
- **T6 was not verified on Linux.** The conclusion (uninstrumented libomp)
  should hold, and `docker/Dockerfile.tsan` with `libarcher` is the way to
  confirm it, but I ran only on macOS/Homebrew libomp.
