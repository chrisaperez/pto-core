## Remediation log (2026-08-15, same day)

All five findings are closed. Each carries a regression test that was confirmed to
reproduce the original defect before the fix landed — the review's own standard, and
the reason its findings existed in the first place.

| # | Fix | Regression test |
|---|---|---|
| 1 | Early return for `len < min_overlap_` before any seed load, `limit` no longer clamped | `fastq_stream/tests/test_trimmer.cpp` → `test_adapter_short_read_overread` |
| 2 | All window/bin guards moved onto `ProfileOptions::validate()`; both entry points and `compute_matrix` call it; `bin_count()` widened to `int64_t` | `cuttag_profiler/tests/test_signal_calc.cpp` → four `ProfileOptions`/`compute_matrix` cases |
| 3 | Per-byte clamp in `mean_phred`, matching `accumulate_read` | `fastq_stream/tests/test_trimmer.cpp` → `test_mean_phred_underflow` |
| 4 | `n * k` overflow rejected; per-thread state hoisted out of the parallel region; loop runs through `parallel_for_checked<64>` | `scrna_matrix/tests/test_matrix_ops.cpp` → `test_knn_k_overflow_is_rejected` |
| 5 | Shared `inv_norm_from_sq` / `normalize_dense_row` helpers accumulating in double, used by all three loops | `scrna_matrix/tests/test_matrix_ops.cpp` → `test_norms_do_not_saturate_on_large_magnitudes` |

Verification: finding 1 reproduced as `heap-buffer-overflow READ of size 4` under ASan
before the fix and is clean after; finding 2's exact payloads
(`upstream: 2000000000` and `upstream: INT64_MAX`) now return HTTP 400 against a live
`serve` instance that survives them.

### Deviations from the patches as written

- **Finding 4** proposed `if (k > n) k = n` alongside the overflow check. Not applied:
  `k` is the documented row stride of the result, and rows with fewer than `k`
  available neighbours are specified to keep `-1`/`0.0f` sentinels in the unused
  slots (`KnnGraph`, and `test_knn_k_exceeds_rows` asserts exactly this). Clamping
  would silently reshape the caller's output. The overflow check alone closes the
  defect.
- **Finding 4** also proposed `thread_local` per-thread state inside
  `parallel_for_checked`. Not applied: a `thread_local BoundedTopK topk(k)`
  initialises once per thread and would then be stale for a second call with a
  different `k`. State is instead built into a `vector<ThreadState>` sized before the
  region, which additionally moves every throwing allocation onto the calling thread.

### New residual, found by finding 5's regression test

A **fourth** site of finding 5's defect class, which the review did not enumerate:
`simd::gather_dot` and `simd::sparse_dot` accumulate the dot product itself in
`float`. For two identical rows scaled to `1e30`, `dot` saturates to `+inf`, and
`cosine_from_dot`'s `!isfinite(r) -> 0` guard then returns **0** — the same "row
matches nothing" outcome as finding 5, reached through the *brute-force* path, which
is the exact k-NN baseline. The norms are already exact (S2 widened
`sparse_norm_sq`); only the dot is narrow.

Not fixed here, deliberately: the only fix is to widen the accumulator in the
`O(n^2)` SIMD kernel that is the module's headline benchmark, which is a performance
trade-off to take deliberately rather than as a drive-by. The behaviour is **pinned**
by an assertion in `test_norms_do_not_saturate_on_large_magnitudes`, which fails
loudly if it changes in either direction.

## 1. High — Heap overread in the adapter seed scan on short reads

`modules/fastq_stream/include/fastq_stream/adapter_trimmer.hpp:75-93`

### What is wrong

```cpp
const std::size_t limit = (len >= min_overlap_) ? (len - min_overlap_) : 0;
...
const bool word_seed = (seed == 4) && (min_overlap_ >= 4);
...
for (std::size_t s = 0; s <= limit && s < best; ++s) {
  if (word_seed) {
    uint32_t w;
    std::memcpy(&w, seq + s, 4);   // <-- reads 4 bytes
```

The in-bounds argument is stated in the comment directly above it:

> Reading 4 bytes at offset `s` is in bounds because `s <= len - min_overlap` and
> `min_overlap >= seed == 4`.

That argument holds **only on the `len >= min_overlap_` branch.** When
`len < min_overlap_` the ternary clamps `limit` to `0` — but `0 <= limit` is still
true, so the loop body executes once at `s = 0` and reads 4 bytes out of a buffer
that has fewer than 4. The clamp was written as if it suppressed the loop; it does
not, because the loop bound is inclusive.

Concretely, with the defaults (`min_overlap_ = 4`, `seed_len_ = 4`) and a read of
length 1, 2 or 3:

| `len` | `limit` | loop runs? | bytes read at `s=0` | overread |
|---|---|---|---|---|
| 0 | — | no (early return) | — | — |
| 1 | 0 | **yes** | 4 | **3** |
| 2 | 0 | **yes** | 4 | **2** |
| 3 | 0 | **yes** | 4 | **1** |
| 4 | 0 | yes | 4 | 0 (exactly in bounds) |

The non-word path has the same shape: `std::memcmp(seq + s, a, seed)` with
`seed = min({seed_len_, min_overlap_, alen})`, which can exceed `len` on the same
branch — so raising `--adapter-seed` or setting `--adapter-overlap 8` does not avoid
it, it widens it.

### Why it is reachable from ordinary input

This is not an adversarial-input finding. `pipeline.cpp:113-115` calls the trimmer on
the **post-quality-trim** span, with no length precondition:

```cpp
if (cfg_.trim_adapters && !trimmer_.empty()) {
  const std::size_t span = end - start;
  const std::size_t kept = trimmer_.trim(r.seq + start, span);
```

Any read that quality-trimming reduces to 1–3 bases reaches it. With the default
`--window 4 --window-mean 20`, a low-quality read is routinely cut to a handful of
bases; `trim_sliding_window` returning a small non-zero value is the normal case, not
a corrupt one. The `--min-len 15` filter that would discard such a read runs
**after** the adapter trim (`pipeline.cpp:124`), so it cannot prevent this.

### Why the existing test and fuzz work missed it

`tests/test_trimmer.cpp` exercises the trimmer only on full-length reads. And the
overread is 1–3 bytes *into the same 256 KiB chunk buffer* in almost every case —
`Buffer` allocates `kPrefix + kChunkBytes` and records sit well inside it, so ASan
sees an in-bounds access and stays silent. It becomes an allocation-crossing read
only when the short read is the last record in the final chunk. That is exactly the
profile of a bug that survives a 36-input adversarial corpus: it is reachable
constantly and detectable almost never.

It is still UB today, and it is a real out-of-bounds read the moment the buffer
layout shifts.

## 2. High — HTTP `/api/profile` bypasses the CLI's window guards

`modules/cuttag_profiler/src/http_server.cpp:257-282` vs `src/main.cpp:163-192`

### What is wrong

Findings S4, S5 and S6 in AUDIT.md were all fixed by adding option validation — but
the validation was added to `main.cpp`, the **CLI** entry point. `ProfileOptions` has
a second entry point: the `POST /api/profile` handler, which builds the same struct
from untrusted JSON and applies only a subset of the same checks.

| Guard | CLI (`main.cpp`) | HTTP (`http_server.cpp`) |
|---|---|---|
| `window_length() > 0` | ✅ :163 | ✅ :279 |
| `bin_size > 0` (S4) | ✅ :169 | ✅ :259 (via `std::max(1, ...)`) |
| `upstream/downstream >= 0` (S5) | ✅ :174 | ❌ **missing** |
| 10M-bin ceiling (S6) | ✅ :182 | ❌ **missing** |

S6 was recorded as fixed. It is fixed for the CLI and open for the network path — and
the network path is the one that takes input from a party who is not the operator.

### Consequences

**(a) Unauthenticated remote OOM-kill.** The exact S6 scenario, over HTTP:

```
POST /api/profile
{"bam":"demo.bam","regions":"demo_promoters.bed","upstream":2000000000,"downstream":2000000000}
```

`bin_count()` → 80,000,000. `compute_matrix` (`signal_calc.cpp:153`) then does
`matrix.values.assign(rows * 80e6, 0.0)` — 640 MB of `double` **per region**. The
kernel SIGKILLs the server process with no diagnostic, which is precisely the failure
S6 exists to prevent. Every other in-flight request dies with it. No auth is required;
`--bind` decides who can reach it.

**(b) Signed overflow → UB, before any check runs.** `window_length()` is
`upstream + downstream` on `std::int64_t` (`types.hpp:107`) with no checked
arithmetic:

```
{"upstream": 9223372036854775807, "downstream": 1}
```

overflows *inside* `window_length()`, so the `<= 0` guard at :279 is evaluating an
already-undefined value. This is S5's defect class — signed overflow on an
attacker-influenced coordinate — reappearing in the function S5's fix did not touch.
UBSan will flag it as `signed integer overflow in types.hpp:107`.

**(c) `static_cast<int>` narrowing.** With `binSize: 1` and a 4e9 window,
`bin_count()` narrows an `int64_t` of 4e9 into `int` — implementation-defined, and on
x86-64 clang yields a negative count that then fails the `nbins <= 0` check with a
misleading "profile window is empty" error rather than the real cause.

**(d) Negative half-windows.** `{"upstream": -100000, "downstream": 200000}` sums
positive, passes :279, and reaches `make_window` with a negative `left`. The checked
builtins there prevent UB, but `bin_offsets` is then computed as
`-opts.upstream + (lo + hi) / 2` (`signal_calc.cpp:163`), silently producing a
profile whose x-axis is mislabelled — a wrong scientific result reported as success.

### Patch

The durable fix is to move validation off both entry points and onto the type, so a
third caller cannot reintroduce the gap.

## 3. High — S3's quality underflow is still live in `mean_phred`

`modules/fastq_stream/include/fastq_stream/phred_calculator.hpp:209-213`

### What is wrong

AUDIT.md S3 records the unsigned underflow in `accumulate_read` as fixed, and it is —
the comment at :139-152 explains the fix at length. But the *identical expression*
sits 50 lines below, unmodified:

```cpp
inline double mean_phred(const uint8_t* qual, std::size_t len) noexcept {
  if (len == 0) return 0.0;
  const uint64_t s = simd::sum_u8(qual, len) - static_cast<uint64_t>(len) * kPhredOffset;
  return static_cast<double>(s) / static_cast<double>(len);
}
```

This is character-for-character the construct S3 was written to eliminate. Any quality
byte below the `+33` offset makes the subtraction wrap in `uint64_t`.

### Why this one is worse than S3

S3 corrupted a *reported statistic* — the summary said Q4611686018427387904 and a
human noticed. `mean_phred` is not a statistic. It gates a **drop decision**
(`pipeline.cpp:135-139`):

```cpp
if (cfg_.min_mean_q > 0.0 &&
    mean_phred(r.qual + start, final_len) < cfg_.min_mean_q) {
  st.dropped_short += 1;
  return true;                       // dropped
}
```

The wrap produces a value around `1.8e19`, so `mean_phred(...) < cfg_.min_mean_q` is
**false** and the read is **kept**. The filter inverts precisely on the input it
exists to reject: the lowest-quality reads in the file are the ones that survive it.

Worked example — four bases with quality bytes `\x01\x02\x03\x04`:

| quantity | value |
|---|---|
| `sum_u8` | 10 |
| `len * 33` | 132 |
| `10 - 132` as `uint64_t` | 18446744073709551494 |
| `mean_phred` | ≈ 4.6e18 |
| `--min-mean-q 20` verdict | **kept** (correct verdict: dropped) |

Silent, no diagnostic, and it moves bad data downstream into the aligner.

### Why it was missed

`tests/test_trimmer.cpp:215` is the only `mean_phred` test and it asserts
`mean_phred(g, 50) > 39.9` on an all-`'I'` (Q40) buffer — it only exercises the
high-quality direction. S3 was found by fuzzing `accumulate_read`; nothing fuzzes the
filter path.

### Patch

```diff

+++ b/modules/fastq_stream/include/fastq_stream/phred_calculator.hpp

+  // Clamp per byte, exactly as accumulate_read does. The previous form,
+  //     simd::sum_u8(qual, len) - len * kPhredOffset
+  // is the same unsigned underflow fixed in accumulate_read (AUDIT.md S3): any
+  // quality byte below the +33 offset wraps the uint64_t subtraction to ~1.8e19.
+  //
+  // Here that is worse than a bad statistic. This function gates the
+  // --min-mean-q drop in pipeline.cpp, and a wrapped mean is enormous, so the
+  // `< min_mean_q` test fails and the read is KEPT. The filter inverted on
+  // exactly the corrupt input it exists to reject.

```

The scalar loop is not a regression: this runs once per surviving read over
`final_len` bytes, against the four full passes already made over the same read, and
it removes a separate `sum_u8` traversal — the same reasoning recorded for the S3 fix.

Regression test:

worth having), but it is worth a comment saying no production path may use it
without clamping first.

## 4. Medium — Exceptions escape the brute-force OpenMP region

`modules/scrna_matrix/include/matrix/knn_graph.hpp:147-155`

### What is wrong

AUDIT.md finding 4 identified exceptions escaping `#pragma omp parallel` as UB that
libomp turns into `std::terminate`, and fixed it with `parallel_for_checked`. That
helper is used for both HNSW regions. The **brute-force** path has a third parallel
region, and it was not converted:

```cpp
  #pragma omp parallel
  {
    detail::BoundedTopK topk(k);              // heap_.reserve(k)  -> can throw
    simd::DenseScratch scratch;
    if constexpr (std::is_same_v<T, float>) {
      scratch.resize(mat.cols());             // buf_.assign(...)  -> can throw
    }
```

Both statements allocate, inside the structured block, with no `try`. `reserve` throws
`std::length_error` or `std::bad_alloc`; `assign` throws `std::bad_alloc`.

### Reachable path

`k` is a `std::size_t` straight from Python (`python_bindings.cpp:218`) with no upper
bound. Note the ordering that makes this deterministic rather than
memory-pressure-dependent:

```python
scrna_matrix_py.build_knn_graph(mat, k=2**62)   # mat has 4 rows
```

1. `graph.neighbor_idx.assign(n * k, -1)` at :134 — `n * k` = `4 * 2**62` wraps to
   **0**. No allocation, no throw. The overflow is what lets execution reach the
   parallel region at all.
2. `#pragma omp parallel` opens.

## 5. Medium — S2's float-square overflow survives in three HNSW norm loops

`modules/scrna_matrix/include/matrix/knn_graph.hpp:341-343, 429-435, 446-447`

### What is wrong

AUDIT.md S2 is a good finding: `1e30` is an ordinary float, `1e30² = 1e60` saturates
to `inf`, and `inf/inf` is NaN. The fix introduced `WideAcc<T>` and applied it in
`simd::sparse_norm_sq` (`simd_math.hpp:96-101`), with a clear comment.

Three hand-rolled norm loops in `knn_graph.hpp` accumulate in **`float`** and were not
updated:

```cpp

for (const float v : val) norm_sq += v * v;
const float inv = (norm_sq > 0.0f) ? 1.0f / std::sqrt(norm_sq) : 0.0f;

// :429-435 (dense build) and :446-447 (dense query), same shape

const float inv = (norm_sq > 0.0f) ? 1.0f / std::sqrt(norm_sq) : 0.0f;
```

### Consequence

The failure is quieter than S2's but the same root cause. With any element ≥ ~1e19,
`norm_sq` saturates to `+inf`. Then:

- `norm_sq > 0.0f` is **true**, so the zero-guard does not fire;
- `inv = 1.0f / std::sqrt(inf)` = `1.0f / inf` = **`0.0f`**;
- every component is written as `v * 0.0f` = `0.0f`.

The row is inserted into the index as an **all-zero vector**. Its inner product with
everything is 0, so its cosine distance to every point is exactly 1.0 — it matches
nothing, and its k-NN list is arbitrary. No exception, no warning, no NaN for a
downstream check to catch. The comment at :422-423 states the intent exactly — "a NaN
row would otherwise ... be silently indexed as an all-zero vector that matches
nothing" — and the finiteness check added there does prevent the NaN route, while this
overflow route reaches the same bad state from finite input.

`Block_CSR::validate()` does not prevent it either: it rejects non-finite *values*,
and `1e30` is finite. That is precisely the gap S2 documented ("boundary finiteness
checking was necessary but not sufficient") — the lesson was recorded but applied to
only one of the four sites.

## Examined and cleared

Checked in this pass and found sound. Recorded so the next reviewer does not repeat it.

- **`SpscRing` memory ordering** (`lockfree_queue.hpp`) — correct. `try_push` writes
  the slot before the release-store of `tail_`; `try_pop` acquire-loads `tail_` before
  reading. The one reserved slot keeps producer and consumer off the same element, and
  the cached-index optimisation is stale only in the conservative direction (a stale
  `cached_head_` makes the ring look fuller, never emptier). The `alignas(kCacheLine)`
  padding on all four indices is real, not decorative.
- **`Buffer::extend_front` / `capacity()`** — `front_` is a signed `ptrdiff_t` and
  goes negative by design; `capacity()` compensates correctly. The assembler bounds
  the prepend against `kPrefix` (`pipeline.cpp:298`) *before* the `memcpy`, and
  `extend_front` is called at most once per chunk, so `front_` cannot accumulate past
  the headroom.
- **`AlignedAllocator`** (`block_csr.hpp:40-49`) — `operator new`/`operator delete`
  with `align_val_t` are correctly paired. `n * sizeof(T)` cannot overflow via
  `std::vector`, which checks against `allocator_traits::max_size()` first.
- **AVX-512 masked tail** (`simd_math.hpp:302-310, 324-327`) — `(1u << remaining) - 1`
  with `remaining` in [1,15] is correct, and the 16-lane bound is genuinely distinct
  from the AVX2 path's 8 rather than a copy-paste. `_mm512_mask_i32gather_ps` does not
  fault on masked-off lanes.
- **AVX2 vs AVX-512 gather argument order** — `_mm256_i32gather_ps(base, index, scale)`
  against `_mm512_i32gather_ps(index, base, scale)`. Both correct; the comment at
  :254-255 flagging the transposition hazard is worth keeping.
- **Function-level `target` attributes over translation-unit ISA flags** — this is the
  right call and the reasoning at `simd_math.hpp:20-28` is sound. Runtime dispatch
  through `isa_level()` is a C++11 magic static, thread-safe, and evaluated after
  static init.
- **`BetterNeighbor` strict weak ordering** (`knn_graph.hpp:47-68`) — a total order
  including the NaN cases: NaN sorts last, ties break deterministically by index.
  The `BoundedTopK` heap direction is right too — with `comp(a,b)` meaning "a scores
  higher", the max-heap root is the *lowest*-scoring element, which is what
  `offer()` displaces.
- **`BufferHandle` lifetime** — `data()`/`size()` computed rather than cached, so a
  copy or move cannot strand a pointer. Re-confirmed.
- **`ScrnaCosineSpace` destruction order** — `space` is declared before `index` in
  both HNSW entry points, so the index (which holds `dist_func_param_` pointing into
  the space) is destroyed first. Re-confirmed at both sites.
- **`knn_graph_to_numpy` capsules** — two independent `shared_ptr<KnnGraph>` capsules,
  one per exported array; each keeps the graph alive independently. Correct.
- **`compute_matrix` worker partitioning** (`signal_calc.cpp:192-256`) — block
  partitioning gives each thread a disjoint `[begin, end)` row stripe, so the writes
  to `matrix.values`, `matrix.row_names` and the reduction buffers are race-free
  without synchronisation. `first_error` is mutex-guarded. The progress loop
  terminates on `first_error`, so a throwing worker cannot hang it.
- **`AlignedBuffer`** (`signal_calc.cpp:25-49`) — rounds up to whole cache lines and
  zero-fills the rounded extent; `count_ == 0` is handled. No false sharing between
  reducers.
- **`hnsw_index_bytes` saturation** — every intermediate is guarded before it can
  wrap, and the function saturates to `SIZE_MAX`, which fails the guard in the safe
  direction. Correct as fixed.
- **`check_narrowing`** (`python_bindings.cpp:130-157`) — rejects non-finite and
  out-of-range before conversion, in both the float and integral branches.
- **`Block_CSR::validate()` strict-increase check** — necessary for the merge-join
  kernel and correctly a `throw` rather than an `assert`, since the gather kernels
  index memory with these values. The reasoning at :270-276 is right.
- **hnswlib misaligned `labeltype` store** (`hnswalg.h:1202`) — confirmed still
  present, still upstream's, still benign on x86-64/arm64. Agree with the existing
  decision not to patch vendored code. Worth an upstream issue.

## A1. Critical — zero-copy adoption borrows memory Python can still change

`Block_CSR::adopt` validates structure once, and the AVX2/AVX-512 gather kernels
then index a dense scratch buffer with the adopted column indices using
*unchecked hardware gathers* — `simd_math.hpp` says so explicitly: "Block_CSR
validates that column indices are in [0, n_cols) at construction time, which is
what makes the unchecked hardware gather below memory-safe."

Adoption broke that guarantee. `is_adoptable` required float32/int32,
C-contiguous, 1-D and 64-byte aligned — but **not** immutability, and NumPy's
own allocator makes stock buffers 64-byte aligned at realistic sizes, so the
common path adopted a fully writeable array. `NumpyOwner` pins the *object*, not
the *buffer*.

Three escapes, all confirmed under ASan, all reachable from pure Python with no
`ctypes` and no threads:

```python
mat = scrna.BlockCSR.from_scipy_csr(data, indices, indptr, n_rows, n_cols)
assert mat.is_zero_copy
indices[0] = n_cols + 4          # (a)
scrna.build_knn_graph(mat, 2, method="brute")
```

- **(a) `indices` mutation → heap-buffer-overflow WRITE of size 4**
  (`knn_graph.hpp:262`, in `DenseScratch::scatter`). Both the offset and the
  written value are attacker-chosen — an arbitrary-write primitive. The only
  guard was an `assert`, and every Release build compiles with `-DNDEBUG`.
- **(b) `indptr` mutation → heap-buffer-overflow READ** (`knn_graph.hpp:212`).
- **(c) `data.resize(k, refcheck=False)` → heap-use-after-free.** NumPy
  reallocates and the adopted pointer dangles.
- **(d) The same as (a) from a second thread** while `build_knn_graph` holds
  `py::gil_scoped_release` — so revalidate-on-entry would *not* have been a
  sufficient fix; the TOCTOU window stays open for the whole kernel.

### Fix

Adopt only buffers that are provably immutable, which on this platform means
buffers we allocated ourselves:

- `to_aligned()` now returns a **frozen** (`writeable=False`), capsule-backed
  array. Measured: NumPy refuses `resize` on it ("does not own its data") and
  refuses `flags.writeable = True` ("cannot set WRITEABLE flag to True of this
  array"). Those two refusals are the whole basis of the in-place path.
- `is_adoptable` additionally requires `!writeable`.

Freezing the *caller's* array would not have worked: NumPy permits
`resize(refcheck=False)` on a non-writeable array, and permits re-enabling
`writeable` on any array that owns its data. Both were measured, and both are
why the fix had to move to "only borrow what we own".

**Behaviour change:** a stock `csr.data.astype("float32")` is no longer adopted
even when aligned — it takes the copy path. Route through `to_aligned()` to keep
zero-copy. `examples/scrna_anndata.py` and `tests/benchmark_1m_cells.py` already
do, so the documented 1M-cell path is unaffected.

Regressions: `test_adopted_buffers_are_immutable`,
`test_adopted_buffers_cannot_be_reallocated`,
`test_adopted_buffers_cannot_be_unfrozen`,
`test_writeable_numpy_buffers_are_never_adopted`.

## A2. High — unbounded request body

`CPPHTTPLIB_PAYLOAD_MAX_LENGTH` defaults to `SIZE_MAX` and
`set_payload_max_length` was never called, so httplib buffers an entire request
body in memory before any handler runs.

Measured against the unpatched build: one 200 MB `POST /api/profile` took the
server from **6.2 MB RSS to 1.51 GB** — ~7.5x amplification, because the body is
buffered, parsed by `nlohmann::json`, then echoed inside the error string. A
few concurrent requests OOM-kill the process, and there is no authentication
(H1) and no CSRF defence (H3), so any page the operator visits can do it.

This is upstream of everything: the `ProfileOptions::validate()` window guards
and `--data-root` confinement both run far too late to help.

**Fix:** `set_payload_max_length(1 MiB)` plus 30 s read/write timeouts (a
slow-loris client otherwise pins a thread from the fixed-size pool), set before
any route is registered. Verified: 200 MB POST → **HTTP 413, RSS +144 KB**;
legitimate requests still return 200.

Not in the scope of the earlier HTTP audit, whose nine findings (H1–L9) all
remain open and are unaffected by this patch.

## A3. Medium — the float dot accumulator has a silent cliff

`simd::gather_dot` and `simd::sparse_dot` accumulate in `float`. Above a
threshold the dot product saturates to `+inf`, and `cosine_from_dot`'s
`!isfinite → 0` guard reports **similarity 0 for two identical rows**. No NaN,
no exception, no warning.

Differential test against an exact double reference, 300x20000 at 2000 nnz/row,
top-15 neighbours:

| value scale | max abs sim error | rows with a different neighbour set |
|---|---:|---:|
| 1e0 – 1e17 | 7.9e-08 | 0 / 300 |
| 1e18 and up | 1.1e-01 | **300 / 300** |

So the earlier characterisation ("possible precision degradation") was wrong in
both directions: below the threshold the float path is exact enough to change
*nothing* — zero rank inversions in 4,500 ranked positions — and above it,
everything is wrong at once. It is a cliff, not a slope.

**Fix:** reject at the boundary rather than widen the hot kernel.
`Block_CSR::validate()` now rejects any row with squared norm above `1e34`,
computed in double during the pass it already makes over every value. By
Cauchy–Schwarz every partial sum of the dot product is bounded by
`||a||·||b|| ≤ 1e34`, four orders of magnitude below `FLT_MAX`. Raw counts, CPM,
log1p and z-scores are all far below the ceiling. The `O(n^2)` kernel is
untouched.

This supersedes the "new residual" recorded in the first pass: that residual is
now unreachable through `Block_CSR`.

`v` passes the flag test, gets adopted, and mutating the base restores the full
heap-buffer-overflow WRITE primitive — re-confirmed under ASan at
`knn_graph.hpp:262`, identical trace to the original finding.

**Fix: provenance, not flags.** `to_aligned()` now stamps its capsule with a
named token (`scrna_matrix.aligned_buffer.v1`), and `is_adoptable` authenticates
that the array's base *is* that capsule, then checks the array still spans
exactly the `AlignedVector` the capsule owns (rejecting reshaped or offset views
that merely inherited it). Only memory this module allocated — to which no
writeable handle can exist, because the sole reference is the capsule — is ever
borrowed. Chasing the base chain instead was rejected: it means re-deriving
NumPy's aliasing rules and keeping them right across NumPy releases.

Lifetime anchoring was hardened alongside it. `NumpyOwner` now acquires the GIL
in its destructor and copy constructor rather than documenting that callers must
hold it. Releasing a `py::object` without the GIL is a decref race inside
CPython; `Block_CSR` is an ordinary C++ value that any future binding could
destroy inside a `gil_scoped_release` region. The capsule destructor also saves
and restores the pending error state, since it runs during deallocation.

Verified: all six PoCs blocked; `to_aligned()` output still adopted zero-copy;
an adopted matrix survives `gc.collect()` with no Python name left for any
buffer. Regressions: `test_readonly_view_over_writeable_base_is_not_adopted`,
`test_only_our_own_capsule_backed_buffers_are_adopted`,
`test_adopted_matrix_outlives_every_python_reference`.

## H2 — the same overflow, one function down

Found by building with a second compiler. `signal_calc` passed under Clang and
failed under GCC 15.

The first pass fixed `window_length()` with `__builtin_add_overflow` but left
`bin_count()` computing `(w + bin_size - 1) / bin_size` unchecked — and
`window_length()` now *saturates to INT64_MAX*, so the overflow became reachable
by design. UBSan: `signed integer overflow: 9223372036854775807 + 50` at
`types.hpp:131`. The result is a large **negative** bin count, so `bins >
kMaxBins` is false and validate()'s ceiling is skipped entirely — reopening the
unauthenticated memory-exhaustion path that ceiling exists to close.

Measured before the fix, `upstream=INT64_MAX, downstream=1, bin_size=50`:
`bin_count() = -184467440737095515`, `validate()` did not throw, on **both**
Apple Clang -O2 and GCC 15 -O2. Being UB it was unstable across optimisation
levels, which is why the Clang Release suite passed while GCC failed.

This is the review's own dominant theme — a fix propagated to one site and not
its sibling — recurring inside the remediation for it.

## H3 — OpenMP is now mandatory

`find_package(OpenMP QUIET)` with a `message(WARNING)` fallback meant `_OPENMP`
was undefined, every `#pragma omp` compiled to serial code, and the suite
reported 100% while never running a parallel iteration. That was the shipping
configuration on the development host.

`modules/scrna_matrix/CMakeLists.txt` now uses `find_package(OpenMP REQUIRED)`
and additionally *proves* the pragmas are live with a `check_cxx_source_compiles`
probe that fails if `_OPENMP` is undefined or a parallel region will not compile
— `find_package` succeeding only shows the compiler accepts the flag. There is
no opt-out variable, by design: building without OpenMP should require editing
the line, so it appears in review and in `git blame`.

The root `CMakeLists.txt` repeats the check so the failure lands at the top of
the configure output with toolchain-specific fixes. It is scoped to
`PTO_BUILD_SCRNA_MATRIX`, because `fastq_stream` and `cuttag_profiler`
contain zero OpenMP code — requiring the toolchain for them would be a
fabricated dependency.

**This breaks the default build on stock macOS/Apple Clang.** That is the
intended behaviour; see the Build section of the README for the two fixes.

`docker/Dockerfile.tsan` (Ubuntu 24.04, clang-18, `libomp-18-dev`, libarcher),
`docker/tsan.supp`, and `scripts/run_tsan.sh` — which probes that
`-fsanitize=thread` *links* and that `-fopenmp -fsanitize=thread` *builds*,

- `fastq_stream` pipeline, `--threads` 2/4/8/16/32, raw and gzip, 60k reads:

## K1 — a real data race, found by the first true TSan run

`hnswlib::HierarchicalNSW::getRandomLevel()` draws from `level_generator_`, a
shared `std::default_random_engine`. `addPoint()` calls it holding only
`link_list_locks_[cur_c]`, a **per-element** mutex, so two threads inserting
different elements hold different locks and read-modify-write the generator
concurrently. Reproducible at 2, 8 and 32 threads via
`scrna::hnsw_build_and_search` (`knn_graph.hpp:591`).

Practical effect on 64-bit targets is a lost update rather than a torn value, so
it degrades to occasional duplicate levels — but it is UB, and it makes index
construction irreproducible beyond hnswlib's documented non-determinism.

Fixed with a dedicated `level_generator_lock_` held only across the draw (not
`global`, which `addPoint` holds across the max-level update — reusing it would
serialise index construction). This is the **first local modification** to the
vendored hnswlib; `third_party/hnswlib/VERSION.txt` no longer claims "verbatim"
and records the patch for the next version bump.

Fixed rather than suppressed, deliberately: a suppression on this call path
would also hide future first-party races routed through it.

## K2 — the suppression file had blinded the harness

The first suppressions included `race:libomp.so` and `race:__kmp_`, intended for
libomp's uninstrumented internal lock pool. TSan matches `race:` against **any
frame in the stack**, and `__kmp_invoke_microtask` appears in the stack of every
race inside *any* OpenMP parallel region — including first-party ones.

Caught by a negative control rather than by inspection: with the K1 fix
deliberately reverted, the harness reported **0** data races. The rules were
replaced with `called_from_lib:libomp.so`, which matches only when the *caller*
of the intercepted function is in libomp. Re-run of the same control: **4** data
races, naming `getRandomLevel`.

Any future change to `docker/tsan.supp` should be validated the same way. A
suppression file that silences the defect you are hunting is worse than none,
because it reports success.

## K3 — mandatory OpenMP, made satisfiable

The previous pass made OpenMP `REQUIRED`, which was right, but it hard-failed on
stock macOS *even after* `brew install libomp`: Apple Clang needs
`-Xclang -fopenmp`, and Homebrew installs libomp keg-only, so `FindOpenMP`
reports NOT FOUND. A clean clone did not configure.

`cmake/PtoOpenMP.cmake` locates the keg (`brew --prefix libomp`, then
`/opt/homebrew/opt/libomp`, then `/usr/local/opt/libomp`, with `-DLIBOMP_ROOT`
overriding) and supplies the variables `FindOpenMP` cannot derive. Shared by the
root and the module so the two cannot drift.

Enforcement is unchanged. Detection is still followed by the
`check_cxx_source_compiles` probe that fails unless `_OPENMP` is defined and a
parallel region compiles — verified by pointing `LIBOMP_ROOT` at a synthetic keg
with a stub `libomp.dylib`: detection fired, `find_package` succeeded, and the
probe **correctly failed the build**. `find_package` succeeding is not
sufficient, and the probe is what makes that true.

Verified paths: no libomp → actionable hard error; `-DPTO_BUILD_SCRNA_MATRIX=OFF`
→ configures; Homebrew GCC → configures, builds, 5/5 tests; standalone module
configure → works. Not verified end-to-end: Apple Clang with a *real* libomp,
because it is not installed on this host. `brew install libomp` then
`cmake -S . -B build` is the one command that closes that gap.

## K4 — lifetime anchoring

`NumpyOwner`'s destructor called `py::gil_scoped_acquire` unconditionally.
`PyGILState_Ensure()` against a finalised interpreter is undefined and typically
crashes; a `Block_CSR` can outlive the interpreter via a static, a leaked module
reference, or an embedding host. It now checks `Py_IsInitialized()` and releases
the handles without decref'ing when the interpreter is gone — the memory is
already reclaimed, so there is nothing to free and nothing safe to decrement.

On the wider question of whether provenance checking is still fragile under
slicing/reshaping: it is not, and the automatic-copy fallback the brief asks for
is already the behaviour. Anything that is not exactly one of our own
capsule-backed allocations — including every slice, reshape and view, whose base
is the ndarray rather than the capsule — takes the copy path. Verified: a
whole-array view of an adopted buffer is copied, not adopted.

New permanent tests: `test_adoption_does_not_leak_references` (refcounts stable
across 50 adopt/destroy cycles), `test_concurrent_adopt_and_knn_from_python_threads`
(8 threads × 25 adopt/knn/destroy with the GIL released inside the kernel),
`test_knn_arrays_outlive_their_graph`. All clean under ASan.

### Lock-order inversions: attributed, not dismissed

TSan's deadlock detector emitted ~7,560 lock-order-inversion reports across six
runs, all with **null stacks** (`#0 <null> <null>`), which makes them both
unattributable and unsuppressible — TSan suppressions match on frames.

Attributed by experiment: building with `-DSCRNA_ENABLE_HNSW=OFF` drops them to
**zero** while leaving all first-party parallel code in place. They are
inversions between hnswlib's per-element mutexes (`link_list_locks_[cur_c]` vs
`link_list_locks_[neighbour]`), which two threads with overlapping neighbour
sets can acquire in opposite orders. That is a **genuine potential deadlock in
upstream hnswlib**, not a false positive, and it is recorded as such.

Not fixed: it requires restructuring hnswlib's locking, a change to vendored
code with a worse risk profile than the residual, and it is not observed to
deadlock at the concurrency this library uses. The detector is off by default in
the harness (`TSAN_DETECT_DEADLOCKS=1` re-enables); the rationale is in
`docker/tsan.supp` §2.

### Observed flake

One of six harness runs (32 threads) exited nonzero from the Python suite while
reporting `34 passed` — a process-exit anomaly at teardown, not a test failure
and not a race. Six direct repetitions of that exact configuration all exited 0.
Recorded rather than smoothed over; worth watching if it recurs.

## What CI is built to catch

Not a generic build-and-test. Each job exists because a specific class of defect
got through during this hardening effort:

- **A silently single-threaded build.** Every matrix job greps
  `SCRNA_OPENMP_PRAGMAS_ACTIVE:INTERNAL=1` out of `CMakeCache.txt` before
  trusting a green test run, and `config-matrix` asserts that configuring
  *without* OpenMP still hard-fails *and* still prints its remediation steps. If
  that assertion ever passes, the requirement has decayed back into a warning.
- **Compiler-specific UB.** GCC and Clang both run, because a signed-overflow
  bug in `bin_count()` passed under one and failed under the other at the same
  optimisation level.
- **Sanitizer runs that quietly do not run.** The ASan job runs the native
  binaries and the Python suite as *separate* steps: the C++ targets link the
  runtime themselves and abort if it is preloaded again, while the Python suite
  must have it preloaded because it dlopens an instrumented module into a stock
  CPython. Running them together silently breaks one or the other.
- **macOS toolchain rot.** A `macos-14` job with Homebrew `libomp` is the only
  place `cmake/PtoOpenMP.cmake`'s keg auto-detection is exercised.
- **TSan**, containerised, across thread counts.

### -Werror was tried and rejected

A global `-Werror` fails on the vendored hnswlib and, on arm64, inside GCC's own
`arm_neon.h` — neither a defect here. CI instead greps the build log and fails
on any warning whose path is under `modules/*/{src,include,tests}`, excluding
`third_party`. Precise, and not defeatable by a compiler-header false positive.

Two real issues surfaced while testing this: `hnswlib` was not included with
`SYSTEM` (so its warnings polluted first-party output — fixed), and
`benchmark.cpp`'s `sink()` had a genuine `-Wunused-but-set-variable` (fixed).

## Note on process

While applying F1 a scripted edit deleted ~150 lines of `http_server.cpp` —
every helper between the Host/Origin block and the end of the anonymous
namespace. The file was untracked, so there was no `git restore`; it was
recovered from the `pto-tsan` Docker image, which carries a `COPY` of the
tree from before the edit. The changes were then re-applied with an assertion on
every substitution (`assert s.count(old) == 1`) so a silent no-match or an
over-broad match fails loudly instead of quietly corrupting the file.

**This repository is not under version control.** That is the single highest-value
gap remaining: `git init` at the root would have made the above a one-command
recovery instead of a lucky one.
